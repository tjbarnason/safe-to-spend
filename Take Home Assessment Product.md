# Take-Home Assessment

## Overview

This is an async, spec-driven product exercise designed to evaluate how you think, design, and build using AI-first workflows. You will identify a problem worth solving, define requirements, design a system, and implement a working application using Kiro.

**Time expectation:** 3–5 hours (not timed — complete at your own pace within 5 business days)
**Deliverable:** A public GitHub repository containing your complete project

---

## The Challenge

Build something useful in the personal finance or fintech space — for example, loan origination, payments processing, account onboarding, budgeting, credit decisioning, or another idea or tool that showcases your experience and capabilities.

You decide what to build, who it's for, and why it matters. Pick something that lets you demonstrate product thinking, not just technical ability.

### Constraints

1. **Domain:** Your application must be relevant to personal finance, banking, or fintech. It should solve a real problem a real user might have.

2. **External API integrations:** If it makes sense for your build, integrate one or more public APIs. The choice of API should serve your product — pick whatever supports the experience you're building.

3. **Built with Kiro:** The project must be built using Kiro's spec-driven workflow. Other AI tools (ChatGPT, Claude, Copilot, etc.) can be used as supplementary aids for research, brainstorming, or debugging — but Kiro should be your primary development environment and the spec workflow should drive your implementation. If you haven't used Kiro before, that's fine — figuring it out is part of the exercise.

4. **Published and runnable:** Your completed project must be in a public GitHub repository. Ideally, host a live demo (Vercel, Netlify, Railway, etc.) — but at minimum, a user should be able to clone the repo and run it locally with clear setup instructions.

---

## What You Must Deliver

Your GitHub repository must contain:

### 1. Kiro Spec Artifacts

Your project should include spec artifacts generated through Kiro's spec workflow — each containing requirements, design, and tasks. How you organize your specs — whether as a single feature or multiple increments — is a product decision.

We will review the spec quality as heavily as the code. These should reflect your product thinking — not just a restatement of this brief.

### 2. AI Collaboration Context

We need to understand how you worked with AI throughout this exercise. Context is critical — we want to see your thought process, decisions, and iterations as they happened.

**Important:** Set up a Kiro hook to capture session context and collaboration history automatically. This gives us insight into how you actually work with AI — the prompts you write, the decisions you make, and how you iterate. How you structure and organize that captured context is up to you, but it should tell the story of your development process in real time, not as an after-the-fact summary.

### 3. A Working Application

It must run. Technology stack is your choice. For anything with a front-end, design and user experience matter — we're evaluating product thinking, and that includes how the experience looks and feels, not just whether it functions.

### 4. A README.md

- What you built and why — what problem does it solve? Who is the user?
- Which APIs you integrated and how they serve the product
- How to run it locally (and link to live demo if hosted)
- Product decisions you made and your reasoning
- What you would change or add with more time

## What We're Evaluating

| Dimension | What We're Looking For |
|-----------|----------------------|
| **Product Thinking** | Did you identify a real problem? Can you articulate who the user is and why this matters? Are your requirements driven by user needs? For front-end work, does the design reflect thoughtful UX — layout, hierarchy, clarity, and polish? |
| **Spec Quality** | Are the requirements clear, testable, and well-structured? Does the design show real technical thinking — data flow, error handling, API patterns, edge cases? Are tasks logical and incremental? |
| **Technical Fluency** | Does the code work? Do you handle API errors, loading states, and edge cases? Is the integration pattern clean? Can you read and understand what Kiro generated? |
| **AI Collaboration** | How effectively did you use Kiro? Did you iterate on the problem and specs before jumping to code? Does the captured context show thoughtful collaboration — not just prompting, but genuine back-and-forth that shaped the product? |
| **Ambiguity Navigation** | We intentionally left the problem open-ended. How did you handle that? Did you make decisions and move forward, or did you get stuck waiting for direction? |
| **Code Quality** | Is the code organized, readable, and maintainable? We don't expect production polish, but we expect someone who understands what good looks like. |

## Tips

- **Start with the problem, not the solution.** The best submissions have a clear point of view on the user and the problem before any code is written.
- **Show your thinking.** Your repo should tell the story of how you got to the final result — not just the final result. The collaboration context hook is how we see this.
- **Scope is a product skill.** Knowing what to build and what to cut matters as much as execution.
- **Design matters.** If your app has a UI, it should look intentional. You don't need to be a designer, but we notice when someone cares about the experience.
